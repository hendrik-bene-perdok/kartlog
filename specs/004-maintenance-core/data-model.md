# Data Model: Kart Maintenance Core System

**Feature**: 004-maintenance-core  
**Date**: 2026-02-08  
**Phase**: 1 - Data Design

## Overview

This document defines the data entities, relationships, validation rules, and state transitions for the kart maintenance system. All entities are stored in Firestore with offline persistence enabled.

---

## Entity Definitions

### 1. Kart

Represents a go-kart unit with its maintenance configuration and current status.

**Firestore Collection**: `karts`

**Schema**:
```typescript
interface Kart {
  id: string;                    // Auto-generated Firestore document ID
  userId: string;                // Owner reference (for future multi-user support)
  name: string;                  // e.g., "Kart #17", "Kart #80"
  totalEngineHours: number;      // Computed field: sum of all session durations (in hours)
  thresholds: MaintenanceThreshold[]; // Pre-configured maintenance intervals
  createdAt: Timestamp;
  updatedAt: Timestamp;
}

interface MaintenanceThreshold {
  type: string;                  // e.g., "Oil Change", "Air Filter", "Valve Adjustment"
  intervalHours: number;         // e.g., 10 (baseline for threshold)
  yellowWarningHours: number;    // e.g., 8 (Medium priority task trigger)
  redWarningHours: number;       // e.g., 10 (High priority task trigger)
  lastCompletedAt?: Timestamp;   // When this maintenance was last done (resets counter)
}
```

**Default Thresholds** (pre-configured for new karts):
```typescript
const DEFAULT_THRESHOLDS: MaintenanceThreshold[] = [
  {
    type: 'Oil Change',
    intervalHours: 10,
    yellowWarningHours: 8,
    redWarningHours: 10
  },
  {
    type: 'Air Filter',
    intervalHours: 25,
    yellowWarningHours: 22,
    redWarningHours: 25
  },
  {
    type: 'Valve Adjustment',
    intervalHours: 50,
    yellowWarningHours: 45,
    redWarningHours: 50
  }
];
```

**Validation Rules** (Zod schema):
- `name`: Non-empty string, max 50 characters, required
- `totalEngineHours`: Non-negative number, >= 0, required
- `thresholds`: Array of at least 1 threshold, each with:
  - `type`: Non-empty string
  - `intervalHours`: Positive number > 0
  - `yellowWarningHours`: Positive number, must be ≤ `redWarningHours`
  - `redWarningHours`: Positive number, must be ≤ `intervalHours`

**Relationships**:
- 1 Kart → Many SessionLogs (one-to-many)
- 1 Kart → Many MaintenanceTasks (one-to-many)
- 1 Kart → Many ShoppingListItems (one-to-many)

**State Transitions**:
- **Created** → Initialized with `totalEngineHours = 0` and default thresholds
- **Hours Updated** → When SessionLog added, `totalEngineHours` incremented via transaction
- **Threshold Customized** → User edits warning hours, persisted immediately
- **Deleted** → Cascade delete all related SessionLogs, MaintenanceTasks, ShoppingListItems (requires confirmation)

### 2. SessionLog

Represents a single driving/running session for tracking engine hours.

**Firestore Collection**: `sessionLogs`

**Schema**:
```typescript
interface SessionLog {
  id: string;                    // Auto-generated Firestore document ID
  kartId: string;                // Foreign key to Kart
  userId: string;                // For filtering in multi-user scenarios
  durationMinutes: number;       // Input from user (e.g., 45 minutes)
  durationHours: number;         // Computed: durationMinutes / 60
  notes?: string;                // Optional session notes
  loggedAt: Timestamp;           // When this session occurred (defaults to now)
  createdAt: Timestamp;          // When this log entry was created
}
```

**Validation Rules**:
- `kartId`: Non-empty string, must reference existing Kart
- `durationMinutes`: Positive integer, 1 <= duration <= 1440 (max 24 hours per session)
- `notes`: Optional string, max 200 characters
- `loggedAt`: Valid timestamp, cannot be future date

**Relationships**:
- Many SessionLogs → 1 Kart (many-to-one)

**State Transitions**:
- **Created** → Triggers Kart `totalEngineHours` update via Firestore transaction
- **Deleted** → Decrements Kart `totalEngineHours` via transaction

**Business Rules**:
- When created: `kart.totalEngineHours += sessionLog.durationHours` (atomic transaction)
- Trigger warning zone re-evaluation after creation

### 3. MaintenanceTask

Represents a maintenance or repair task to be completed.

**Firestore Collection**: `maintenanceTasks`

**Schema**:
```typescript
interface MaintenanceTask {
  id: string;                    // Auto-generated Firestore document ID
  kartId: string;                // Foreign key to Kart
  userId: string;
  description: string;           // e.g., "Replace brake pads on Kart #80"
  priority: 'High' | 'Medium' | 'Low'; // Task urgency
  status: 'pending' | 'completed'; // Task completion state
  isAutoGenerated: boolean;      // true if created by warning zone system
  autoGeneratedType?: string;    // e.g., "Oil Change" (if auto-generated)
  createdAt: Timestamp;
  completedAt?: Timestamp;       // Null until marked complete
}
```

**Validation Rules**:
- `kartId`: Non-empty string, must reference existing Kart
- `description`: Non-empty string, max 200 characters
- `priority`: Enum: 'High' | 'Medium' | 'Low'
- `status`: Enum: 'pending' | 'completed'
- `isAutoGenerated`: Boolean, if true then `autoGeneratedType` required

**Relationships**:
- Many MaintenanceTasks → 1 Kart (many-to-one)

**State Transitions**:
- **Created** → Status = 'pending', completedAt = null
- **Completed** → Status = 'completed', completedAt = Timestamp.now()
- **Deleted** → Hard delete from collection

**Business Rules**:
- **Auto-generation**: When kart's total hours crosses red threshold AND no pending task with same `autoGeneratedType` exists, create High priority task
- **Yellow zone**: Create Medium priority task when crossing yellow threshold
- **Duplicate prevention**: Query existing pending tasks with matching `kartId + autoGeneratedType` before creating auto-task

### 4. ShoppingListItem

Represents a part or component to purchase.

**Firestore Collection**: `shoppingListItems`

**Schema**:
```typescript
interface ShoppingListItem {
  id: string;                    // Auto-generated Firestore document ID
  kartId?: string;               // Optional foreign key to Kart (null if general item)
  userId: string;
  description: string;           // e.g., "Brake pads - front"
  photoId?: string;              // Reference to IndexedDB photo blob ID
  status: 'active' | 'ordered' | 'archived'; // Purchase lifecycle
  createdAt: Timestamp;
  orderedAt?: Timestamp;         // When marked as ordered
  archivedAt?: Timestamp;        // When removed (moved to archive)
}
```

**Validation Rules**:
- `description`: Non-empty string, max 200 characters
- `kartId`: Optional string, if provided must reference existing Kart
- `photoId`: Optional string (UUID)
- `status`: Enum: 'active' | 'ordered' | 'archived'

**Relationships**:
- Many ShoppingListItems → 0 or 1 Kart (optional many-to-one)
- 1 ShoppingListItem → 0 or 1 Photo (one-to-one, stored in IndexedDB)

**State Transitions**:
- **Created** → Status = 'active', archivedAt = null
- **Marked Ordered** → Status = 'ordered', orderedAt = Timestamp.now()
- **Removed** → Status = 'archived', archivedAt = Timestamp.now()
- **Auto-deleted** → If archivedAt < (now - 12 months), hard delete

**Business Rules**:
- **Active items**: Query where `status == 'active' OR status == 'ordered'`
- **Archive** (Purchase History): Query where `status == 'archived'`
- **Cleanup**: On dashboard mount, delete documents where `archivedAt < (Timestamp.now() - 12 months)`

### 5. Photo (IndexedDB)

Represents a compressed photo stored locally.

**IndexedDB Database**: `kartlog-photos`  
**Object Store**: `photos`

**Schema**:
```typescript
interface Photo {
  id: string;                    // UUID generated client-side
  blob: Blob;                    // Compressed JPEG blob (<500KB)
  originalFileName: string;      // For debugging/reference
  compressedSizeKB: number;      // Actual size after compression
  createdAt: number;             // Unix timestamp (milliseconds)
}
```

**Storage Strategy**:
- Index by `id` (primary key)
- Photos referenced by `ShoppingListItem.photoId`
- No auto-cleanup (deleted when parent ShoppingListItem deleted)

**Validation Rules**:
- `blob.size`: Must be < 512,000 bytes (500KB)
- `blob.type`: Must be 'image/jpeg'

## Computed Fields & Aggregates

### Kart Dashboard Status

**Real-time computation** (client-side hook):
```typescript
interface KartDashboardStatus {
  kartId: string;
  name: string;
  totalEngineHours: number;
  pendingTaskCount: number;          // Count of MaintenanceTasks where status='pending'
  warningZones: WarningZoneStatus[]; // Green/yellow/red per threshold
}

interface WarningZoneStatus {
  thresholdType: string;        // e.g., "Oil Change"
  zone: 'green' | 'yellow' | 'red';
  priority: 'High' | 'Medium' | null;
  hoursUntilRed: number;        // redWarningHours - totalEngineHours
}
```

**Query Strategy**:
1. Load all karts for user
2. For each kart, load count of pending tasks: `query(collection('maintenanceTasks'), where('kartId', '==', kartId), where('status', '==', 'pending'))`
3. Evaluate warning zones client-side using `lib/services/warningZones.ts`

## Data Access Patterns

### Critical User Flows

**1. Dashboard Load** (User Story 1):
```
Query: collection('karts').where('userId', '==', currentUserId)
  → For each kart:
    - Read totalEngineHours from doc
    - Query count of pending tasks
    - Compute warning zones
```

**2. Log Session** (User Story 2):
```
1. Create SessionLog document
2. Update Kart.totalEngineHours via transaction:
   runTransaction(db, async (txn) => {
     const kartDoc = await txn.get(kartRef);
     const newTotal = kartDoc.data().totalEngineHours + (durationMinutes / 60);
     txn.update(kartRef, { totalEngineHours: newTotal });
     txn.set(sessionLogRef, sessionLogData);
   })
3. Re-evaluate warning zones (trigger auto-task creation if needed)
```

**3. Auto-Task Generation** (Threshold Crossed):
```
1. Evaluate warning zones for kart
2. For each threshold in red/yellow zone:
   - Query existing tasks:
     query(collection('maintenanceTasks'), 
       where('kartId', '==', kartId),
       where('status', '==', 'pending'),
       where('autoGeneratedType', '==', thresholdType))
   - If no existing task, create new MaintenanceTask with:
     { isAutoGenerated: true, autoGeneratedType: thresholdType, priority: zone === 'red' ? 'High' : 'Medium' }
```

**4. Shopping List with Photos** (User Story 3):
```
1. Capture photo via device camera
2. Compress in Web Worker → get Blob
3. Store in IndexedDB:
   const photoId = uuidv4();
   await photosStore.put({ id: photoId, blob, ... });
4. Create ShoppingListItem with photoId reference
5. On render, load photo from IndexedDB by ID
6. On delete archived item (>12 months), also delete photo from IndexedDB
```

## Indexes & Performance

### Firestore Composite Indexes

**Required indexes**:
1. `maintenanceTasks`: `(kartId ASC, status ASC, createdAt DESC)`
   - For querying pending tasks sorted by creation date
2. `sessionLogs`: `(kartId ASC, loggedAt DESC)`
   - For displaying session history chronologically
3. `shoppingListItems`: `(userId ASC, status ASC, archivedAt ASC)`
   - For archive cleanup query

### IndexedDB Indexes

**Primary key**: `id` (auto-generated UUID)  
**No secondary indexes needed** (lookup always by ID)

**Note**: Current MVP is offline-first with no auth. Future team feature will require these rules:

```javascript
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    // Karts: Users can only access their own karts
```

## Summary

**5 Core Entities**:
1. **Kart** - Central entity with computed totalEngineHours and customizable thresholds
2. **SessionLog** - Immutable time-series data for hour tracking
3. **MaintenanceTask** - Priority-based tasks with auto-generation from warning zones
4. **ShoppingListItem** - Three-state lifecycle (active/ordered/archived) with 12-month TTL
5. **Photo** (IndexedDB) - Compressed images linked to shopping items

**Key Design Decisions**:
- Firestore for all relational data (offline-first)
- IndexedDB for photos (avoid Firestore quota)
- Computed field (`totalEngineHours`) updated via transactions
- Client-side warning zone evaluation (no Cloud Functions needed)
- Cascade delete enforced at application layer (Firestore has no foreign keys)
